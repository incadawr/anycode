# Дизайн: сабагент как дочерняя сессия (TASK.102)

- **Дата:** 2026-08-08
- **Статус:** черновик на ревью владельца
- **Источники:** `working-docs/tasks/TASK.102.md` (§2 разведка по коду 01.08,
  §7 решения владельца 08.08), мокапы
  `working-docs/design/subagent-ui-mockups.html`, пересечения: TASK.97
  (R2/R3), TASK.106, TASK.91, TASK.74.

## 1. Цель

Три боли текущих сабагентов, все три закрываются одним механизмом:

1. **Sync-lock:** сабагент блокирует мастер-сессию на всё время работы;
   на длинной стройке мастер «висит» в ходе.
2. **Непрозрачность:** внутрь сабагента нельзя зайти; карточка эфемерна —
   после перезагрузки сессии от ребёнка остаётся только финальный текст.
3. **Нет стиринга:** бегущему сабагенту нельзя докинуть указание — только
   стоп всего хода.

Системная боль сверху: механизмов сабагентов сегодня **три разных**
(in-process side-chain, one-shot CLI-дети на чужих движках, нативные
Task-дети Claude), и один из них — engine-дети — идёт **мимо
permission-гейта AnyCode** целиком. Целевая архитектура сводит все три
к одному примитиву и закрывает дыру.

## 2. Решения владельца (зафиксированы, здесь не пересматриваются)

1. **Путь Б:** ребёнок = настоящая дочерняя сессия-таб, а не прокачанная
   карточка-оверлей.
2. **Сессия технически, НЕ сессия в UX:** детей нет в списке сессий и
   истории никогда; транскрипт хранится в неймспейсе родителя; удаление
   мастера каскадно вычищает детей; у ребёнка нет самостоятельного имени.
3. **Вход через карточку:** карточка сабагента в транскрипте мастера
   получает «Open»; работает на бегущем и завершённом ребёнке.
4. **Раскладки — «не или, а и»:** один примитив (поверхность ребёнка),
   две раскладки; строим **B** (заход одной панелью, breadcrumb) первым,
   сплит **C/D** — лэйаут-слайсом поверх; **D** (сплит×3, аккордеон) —
   целевая картинка для мульти-детей.
5. **Дефолты v1:** закрытие мастер-таба = каскадная отмена детей;
   упал/завис = ошибка в карточку мастера (таймаут остаётся);
   permission-вопросы ребёнка — в его поверхности + бейдж «ждёт
   разрешения» на карточке; режим auto/ask наследуется от мастера на
   момент спавна.
6. **Steering:** обычный композер внутри ребёнка.
7. **Sync-lock на этапе 1 приемлем;** фоновый join — поздней фазой.
8. **Кросс-провайдерные дети:** по умолчанию ребёнок наследует коннект
   родителя; явный выбор провайдера/модели — опциональный параметр спавна.

## 3. Архитектура

### 3.1 Ребёнок = программно созданный таб

`TabHostManager` (`apps/desktop/src/main/tabs.ts`) уже держит инвариант
«один таб — один utilityProcess» и умеет всё нужное для жизненного цикла.
Новое:

- **Метка родителя.** Сессия ребёнка создаётся с `parentSessionId` (+
  `spawnToolCallId` — какой тул-колл мастера её породил). Метка — часть
  персистентной записи сессии.
- **Скрытие.** Все выборки списка сессий/истории фильтруют
  `parentSessionId != null`. Ребёнок адресуется только через родителя
  (карточка → Open).
- **Хранение в неймспейсе родителя.** Транскрипт ребёнка лежит под ключом
  родительской сессии; удаление мастера каскадно удаляет детей.
  Каскад — на уровне persistence-слоя, не UI (чтобы вычищалось и при
  удалении из истории).
- **Каскадная отмена.** Закрытие мастер-таба при бегущем ребёнке =
  отмена ребёнка (семантика та же, что стоп сабагента сегодня).
  Реап — в TabHostManager: закрытие родителя обходит детей.

### 3.2 Спавн и sync-ожидание (v1)

- Спавн — на уровне host/main, **движко-агностичен**: любой мастер
  (core, Claude, Codex), у которого есть дверь-тул (§6), может породить
  ребёнка на любом движке/коннекте.
- v1 — sync: тул мастера блокируется до терминального события дочерней
  сессии (`loop_end`/ошибка/отмена), результат — финальный текст ребёнка
  (+ статус, + ссылка на транскрипт). Это осознанное сохранение sync-lock
  из решения владельца §2 п.7.
- **Интерфейс тула:** расширяется существующий `Agent`-тул (не новый тул):
  параметр `tier: "inline" | "session"` (дефолт `inline` — лёгкий
  side-chain как сегодня), для `session` дополнительно опциональные
  `provider`/`model` (дефолт — коннект родителя). Один тул = модель видит
  оба яруса в одной схеме и может выбирать осознанно.
- Ошибка/зависание ребёнка: ошибка уезжает в карточку мастера; таймаут
  сабагентов остаётся и для сессий-детей.

### 3.3 Кросс-провайдерность

Сессии уже пинятся к коннекту при создании (`connectionId` per-session,
TASK.45 W10; креды резолвит token-broker по connectionId). Ребёнок-сессия
создаётся тем же путём: `connectionId` родителя по умолчанию, явный — из
параметра спавна. Ничего нового в проводе кредов не требуется; UI выбора
коннекта переиспользует пикер из TASK.106 (этап 1), но не зависит от него —
параметр тула работает и без пикера.

Это закрывает главное ограничение сегодняшней схемы «K3/GLM только
мастера»: Claude-мастер сможет спавнить ребёнка на GLM, Codex-мастер — на
Claude, и все дети едут через полный рантайм с permission-гейтом.

### 3.4 Судьба трёх старых механизмов

- **In-process side-chain** — остаётся дефолтом (`tier: "inline"`): дёшев,
  join бесплатный, подходит для разведки/ревью/механики. (Двухъярусность —
  переспросить при куте, §10.)
- **One-shot engine-дети** (`engine:` в md-профиле) — после появления
  `tier: "session"` объявляются deprecated-маршрутом и мигрируют на
  детей-сессий: тот же бинарь CLI, но в интерактивном рантайме с
  approval-бриджем вместо бесгейтового `claude -p`/`codex exec`.
  Снятие маршрута — отдельным решением после живой эксплуатации.
- **Нативные Task-дети Claude-родителя** — v1 не трогаем, остаются
  свёрнутыми (`parent_tool_use_id`).

## 4. UI

- **Примитив один:** отрисовываемая поверхность ребёнка (транскрипт +
  композер + статус). Раскладка — чистое состояние лэйаута; переключение
  single-pane ↔ сплит ничего не теряет.
- **Карточка в транскрипте мастера:** персона, модель, лента активности
  (персистится — лечится эфемерность), кнопка «Open», бейджи состояний:
  running / **ждёт разрешения** / error / done.
- **B (этап 1):** Open открывает поверхность ребёнка на месте чата мастера,
  breadcrumb «Мастер › ребёнок» для возврата.
- **C/D (лэйаут-слайс):** сплит мастер|ребёнок; D — сплит с N детьми
  аккордеоном. Ядро не трогается, только раскладка.
- Мокапы всех четырёх экранов: `working-docs/design/subagent-ui-mockups.html`.

## 5. Permissions

- У ребёнка **свой permission-broker в своей поверхности** — вопросы
  всплывают там, где на них смотрят; мастер видит бейдж «ждёт разрешения»
  на карточке.
- Режим (auto/ask) **наследуется от мастера на момент спавна**; смена
  режима мастера после спавна на бегущего ребёнка не влияет (простота v1).
- Engine-дети через детей-сессий впервые получают полный permission-гейт —
  закрытие дыры из TASK.102 §2.

## 6. Capability discovery — как модель узнаёт, что это возможно

Знание доносится **декларацией тула, не прозой в системном промпте**:
модель действует по схемам тулов, которые видит.

- **Core-движок** (Vercel AI SDK — Kimi, GLM, любой API-провайдер):
  `Agent`-тул уже регистрируется через `withSubagents`; расширяем его
  схему (`tier`, `provider`, `model`) и описание (что такое ярус «session»,
  когда его брать, что доступные коннекты — из настроек). Системный промпт
  дополняет **политикой** использования (стоимость, когда эскалировать),
  но не является носителем самой возможности.
- **Claude/Codex-мастера:** сегодня `Agent`-тула там нет вообще (boot
  уходит в engine-ветку до `withSubagents`) — никакая правка промпта не
  поможет. Дверь = **MCP-тул от AnyCode**, инжектируемый в CLI-сессию.
  Это пересечение с TASK.97: R2 (MCP-дверь для codex) реализуется этим
  механизмом; R3 (`--agents`-проекция) становится ненужной для целей
  этой задачи — сверить рамку TASK.97 при куте.

## 7. Технические предложения по остатку §6 задачи (мои, в рамках мандата)

- **Лимиты:** максимум **3 бегущих ребёнка-сессии на мастера** и **8 на
  приложение** (каждый — utilityProcess); превышение = ошибка тула сразу,
  не очередь. Квоты токенов v1 не вводим — виден расход в телеметрии.
- **Workflow-дети:** ярус «session» на workflow v1 **не распространяется** —
  только `Agent`-тул. Workflow — отдельный контракт, трогать его сейчас =
  расползание рамки.
- **Фоновый join (поздняя фаза):** канал «outcome ребёнка → новый ход
  мастера» через notification-инжект системным сообщением с очередью при
  занятом ходе. Единственный кусок, меняющий контракт агент-лупа —
  проектируется отдельным доком, когда дойдёт очередь.
- **Глубина дерева:** ребёнок-сессия **не может спавнить своих
  детей-сессий** (v1, как сегодня структурно запрещена рекурсия
  in-process); inline-сабагенты внутри ребёнка — можно.

## 8. Этапность

1. **Дешёвый выигрыш (независим):** персистенс ленты активности карточки +
   read-only «зайти посмотреть» для существующих in-process сабагентов.
2. **Ядро:** ребёнок-сессия с sync-ожиданием + раскладка B + каскады +
   permission-мост. Кросс-провайдерный параметр — здесь же (провод готов).
3. **Лэйаут-слайс:** сплит C, затем D (аккордеон).
4. **Миграция engine-детей** на детей-сессий (закрытие permission-дыры).
5. **Фоновый join** — последним, отдельный дизайн.

Порядок 1↔2 может быть перекроен при куте; 5 — строго последним.

## 9. Тестирование

- Unit: фильтрация детей из списков сессий; каскадное удаление/отмена;
  наследование connectionId и режима; лимиты; блокировка тула до
  терминального события; ошибки/таймауты в карточку.
- Renderer-тесты — `.test.ts` чистыми функциями (vitest-глоб не собирает
  `.test.tsx`).
- **Авто-смоук — гейт каждого слайса:** агент (sonnet) гоняет реальную
  dev-сборку через существующий smoke-channel (dev-only
  `apps/desktop/src/main/automation/`, HTTP-loopback, в master `1284e6f`) —
  механика проверяема автоматически: спавн ребёнка, каскадная отмена/
  удаление, скрытие из списка сессий, наследование коннекта/режима,
  бейдж «ждёт разрешения», Open на бегущем и завершённом.
- **Живой смоук владельца — финальная приёмка этапа**, не заменяется
  авто-смоуком: визуал/UX (раскладка B, сплит, аккордеон D, ощущение
  стиринга) — только глазами; дурабл проекта: живой прогон владельца
  ловит то, что юниты, ревью и авто-смоук не видят (md-preview: 5
  дефектов после зелёных 7950 юнитов).
