## Re-running the live probe

Run `codex-orchestrate-probe.mjs --live --bin PATH --root EMPTY_DIR --auth-from AUTH_JSON` on macOS. An optional `--model` selects a model from `model/list` that supports low effort; otherwise the probe selects an available Luna or mini model. The probe symlinks the supplied auth file into scratch CODEX_HOME and normally runs Codex under a macOS sandbox denying writes to the real auth directory. `ORCH_PROBE_NO_SANDBOX_EXEC=1` disables this guard and requires the caller to enforce the same restriction externally; JSON reports `authWriteGuard` as `external-required`. It seeds two local, read-only MCP fixtures, uses a fresh workspace, and emits a single JSON result with no raw model text, configuration, token or thread ID. The scratch directory itself contains session artifacts and an auth symlink and should be treated as private.

`outcome: completed` means the sequence completed, not that the observed values passed: inspect each result, including marker presence, both sentinel files and whether a write-related tool was observed. Absence of a sentinel without an observed write attempt is inconclusive; the presence of a command or file-change event does not itself prove a write was attempted. `config/read` has no thread ID; MCP status names alone are not proof of callable tool inventory. The OFF marker observation is also limited by prior conversation history. Errors or timeouts produce `outcome: incomplete` and nonzero exit status; the failing step's observations are retained. Token usage/streamed output are monitored and interrupted at the stated limits, but the protocol offers no demonstrated hard output-token cap; the cap is client-side and may be exceeded before a notification arrives. Every RPC and turn has a deadline; teardown terminates the isolated process group.

## Owner-run process isolation and remaining transition gate

The owner ran the alternatives probe on 0.166.0. A new app-server with process `-c mcp_servers.<name>.enabled=false` for both fixture servers and `-c features.multi_agent=false` resumed the same native ID, with seven turns preserved. `config/read` reported both enabled values false and `multi_agent=false`, and neither fixture tool was listed. A further restart without these overrides retained the ID and seven turns, restored both enabled values and `multi_agent=true`, and listed both fixture tools again. The run confirms this configuration/inventory sequence, not actual tool-call denial under all configurations. An ON-config fresh thread also lacked fixture tools even though process-level `config/read` retained ambient settings.

Other owner observations: the collaboration-mode marker was absent; application `additionalContext` marker was visible to the model and in its answer history, but not in non-message history and not established as developer-priority. Resume in a newly launched process with developer instructions in the resume request did not produce the new marker. `config/mcpServer/reload` did not alter the observed inventory in the tested cases. These are observations of the tested prompts and configuration, not universal proofs of absence.

Both experimental schemas explicitly contain `developer_instructions`, `sandbox_mode` and `approval_policy` in Config. In the completed process run, the resumed thread echoed readOnly, networkAccess=false and never, and config/read reported the process developer marker present; the model did not emit the process marker. On restart without overrides, config/read no longer contained it and the old marker was not observed. Thus the tested process developer instructions were not visible to the model; this remains a blocker for developer-priority delivery. A base marker and process marker are reported separately; because earlier marker-bearing responses persist in history, model responses alone cannot conclusively distinguish instruction replacement, addition or removal. The process-only test refuses to start a turn unless the resume response echoes readOnly, networkAccess=false and never.

`thread/inject_items` exists in both experimental schemas and appends raw, untyped Responses API items to model-visible history. The schema does not establish that a developer-role item is accepted, its effective priority, or a safe removal operation. Injection is a poor ON/OFF foundation: even if accepted it changes durable history and any compensating instruction may conflict with earlier ones. Do not inject into the real thread without a separately designed, disposable live test.

The engine owns an AppServerClient per Codex session boot: `startCodexEngine` and `resumeCodexEngine` each create and start a client, and each long-lived client spawns its own app-server. The existing resume path creates a new client, resumes the stored native ID and hydrates `thread/read`; this is a boot/recovery path, not yet an atomic in-place mode transition. `dispose()` cancels pending bridge calls, denies outstanding approvals, interrupts and closes the client, and drains bridge work. An admitted detached child is handed off by the child port, which removes turn-abort propagation and routes terminal reports independently; an in-flight or not-yet-admitted call may instead be cancelled. A transition must be idle and preserve the existing child port, report queue, pending admission state and delivery ownership; the present disposal/boot path does not by itself establish that continuity. Active approvals are denied on dispose, so switching must wait or explicitly settle them, not silently transfer them.

The product currently sends `dynamicTools` on both thread/start and thread/resume, although 0.166.0's experimental resume schema omits the field. A bridge handler being wired does not prove the model receives declarations after restarting. The completed process run called the harmless Agent fixture before restart, after restart with no resume declarations, and after a further restart with the product's undeclared `dynamicTools` field. Each call and fixture reply was observed, establishing availability of the tested route. This is not yet an actual detached-child lifecycle test.

**P5/P6 recommendation and gate:** use a per-session app-server restart plus resume of the same native thread as the candidate ON/OFF transport for process-level MCP isolation; the owner-run test confirms reversible fixture inventory and history across that boundary. Do not claim developer-priority instruction delivery: the process marker was present in config but absent from the model response, so instruction composition/removal remains blocked. The Agent fixture was callable across restarts, while lifecycle tests must still cover detached children, report delivery, approvals and failure quarantine. The decision for context delivery is per-turn `additionalContext`, without a developer-priority claim; do not provide a writable fallback. Include startup latency, temporary unavailability, restart failure, empty threads with no rollout, selection/preset preservation, and profile/config precedence in the design. Restore the base process configuration on OFF and verify the effective inventory before reopening admission.
