Re-run with a reachable authenticated service: verify markers ON/OFF, base instruction preservation, actual tool inventory/calls, named MCP suppression/restoration, native delegation suppression and workspace/outside sentinels. For an empty thread, starting a replacement is a candidate only after defining how to handle thread identity and metadata. For a populated thread, evaluate a server-supported reconfiguration mechanism or an explicitly designed new-thread/history migration if effective resume overrides cannot be established; neither is asserted here to preserve developer priority or history.

## Re-running the live probe

Run `codex-orchestrate-probe.mjs --live --bin PATH --root EMPTY_DIR --auth-from AUTH_JSON` on macOS. An optional `--model` selects a model from `model/list` that supports low effort; otherwise the probe selects an available Luna or mini model. The probe symlinks the supplied auth file into scratch CODEX_HOME and runs Codex under a macOS sandbox denying writes to the real auth directory. It seeds two local, read-only MCP fixtures, uses a fresh workspace, and emits a single JSON result with no raw model text, configuration, token or thread ID. The scratch directory itself contains session artifacts and an auth symlink and should be treated as private.

`outcome: completed` means the sequence completed, not that the observed values passed: inspect each result, including marker presence, both sentinel files and whether a write-related tool was observed. Absence of a sentinel without an observed write attempt is inconclusive; the presence of a command or file-change event does not itself prove a write was attempted. `config/read` has no thread ID; MCP status names alone are not proof of callable tool inventory. The OFF marker observation is also limited by prior conversation history. Errors or timeouts produce `outcome: incomplete` and nonzero exit status; the failing step's observations are retained. Token usage/streamed output are monitored and interrupted at the stated limits, but the protocol offers no demonstrated hard output-token cap; the cap is client-side and may be exceeded before a notification arrives. Every RPC and turn has a deadline; teardown terminates the isolated process group.
